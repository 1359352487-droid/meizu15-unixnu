# 交接包：Meizu 15 上的 XNU（UniXNU / HakiOS）—— 2026-11-26 凌晨

> 给下一个接手的人（或下一台机器上的我）。这份文档按"你需要知道什么才能接着干"来组织，
> 不按时间顺序。完整过程在 `docs/STATUS.md`（18 条补记）。

## 一句话状态

**内核已经在真机上跑起来了**（launcher → DarwinBoot → XNU，停在 `Data abort`），
P2（给内核一个可挂载的根卷）还没完成。固件、payload、内核三层的构建链路全部本地可复现。

## 目标

`docs/README-FIRST.md` 是给用户的入口。核心目标是 P2：让 XNU 在 Meizu 15（SDM660 / M8810）
上有一个能挂载的根卷，从"跑到 `bsd_init` 就 panic（no root device）"推进到"能 exec 用户态"。

## 五个关键发现（按踩坑顺序）

### 1. `Meizu15Launcher.c` 不是死代码，反而是唯一推手

它是**唯一**读 `unixnu.toml`、**唯一**调用 `UniXNULoader` 协议（DarwinBoot 安装的）的程序。
`MODULE_TYPE = UEFI_APPLICATION`，所以放进 FDF 也不会自动执行——必须靠
`EFI/BOOT/BOOTAA64.EFI`（BDS 的 removable-media 路径）被 BDS 拉起。

### 2. 16 MiB payload 上限可以绕开：DarwinBoot 解 LZMA

`DarwinBoot.c` 读完内核后判断首字节 `0x5D`，就按 EFI LZMA（5 字节 props + 8 字节 size + 流）解压，
其它情况原样使用。`out/lzma-pack.py` 打包。17.5 MB 的 25 驱动内核压到 4.37 MB。
`DarwinBoot.inf` 需要 `LzmaCustomDecompressLib`，`meizu15.dsc` 里要补它的实例行。

### 3. `Media.LogicalPartition` 必须为 `FALSE`

`FatPkg/EnhancedFatDxe/Fat.c:FatDriverBindingSupported()` 第一件事就是
`OpenProtocol(..., &gEfiDiskIoProtocolGuid, ...)`，没有 DiskIo 直接不支持。
`Meizu15PayloadDxe` 只装 BlockIo + DevicePath，DiskIo 由 `DiskIoDxe` 在 BlockIo 之上安装——
但 `LogicalPartition = TRUE` 会让整条 Disk/Partition 栈把它当"分区"而不是整盘，DiskIo 就没装上去。
**改成 `FALSE` 之后 FatDxe 才挂载，`SimpleFileSystem` 才出现，BDS 才会启动 `EFI/BOOT/BOOTAA64.EFI`。**

这一段是整晚的转折点：屏幕从 `Shell>` 变成内核输出。

### 4. 真机诊断要靠 DEBUG，不是 Print

`PayloadDxe` 里 `Print(L"...")` 在 DXE 这个阶段没有 console，输出会丢；`DEBUG((DEBUG_ERROR, ...))`
能上屏。`…-blockprobe.img` 就是靠这个拿到了 `block0 oem=[BSD 4.4] type=[FAT12   ] sig=55AA`
和 `ConnectController pass 1: Success`。

### 5. ESP 的 FAT 布局不是问题

`hdiutil` 造的 FAT16（1 KiB 簇）和 FAT12（4 KiB 簇，对齐 CI 的 `mformat -c 8`）都试过，
`fsck_msdos` 都通过，两者都停在 `Shell>`——**FAT 布局不是原因**，真正的原因是第 3 条。
`out/make-esp.sh` 现在用 `-fsargs "-c 8"` 生成 FAT12，和 CI 同构。

## 当前卡点：`Data abort: Translation fault, third level`

最后一张屏（`images/boot-meizu15-payload-logical.img` 启动后）：

```
SetupAPSCpuPerfLevels: Failed to get the maximum performance level for CPU 0
Data abort: Translation fault, third level
PC 0x0000000C91F0584   (Meizu15Launcher.dll)
[0] DarwinBoot.dll   [1] Meizu15Launcher.dll   [2] DxeMain.dll   [3] BdsDxe.dll
FAR 0x000000001000BF0  ESR EC 0x25 (data abort, same EL, third level)
```

`PC` 落在 launcher/DarwinBoot 一侧，`FAR = 0x1000BF0`（16 MiB 附近）。
崩溃点在 `DarwinBoot.c` 的段拷贝循环：

```c
CopyMem ((VOID *)(UINTN)(Address + Kernel.Segments[Index].Address - Kernel.Base),
         (UINT8 *)Image + Kernel.Segments[Index].FileOffset,
         (UINTN)Kernel.Segments[Index].FileSize);
```

**两个待验假设**（按可能性排序）：

1. **`Address` 不可写**——`AllocateWindow()` 在 `DarwinBoot.c:864` 返回的地址落在一块
   没有页表映射的区域（函数注释说它"取最高的能放下的地址"，容易撞到 MMIO 或保留区）。
   验证方法：把 `Address` 和 `Used` 打到屏上，对照 `0x1000BF0`。
2. **LZMA 解压后的 `Image` 与 `Kernel.Base/Segments` 不同源**——解压是对 `Image` 做的，
   但 `Kernel` 结构是从**解压前**的缓冲区解析的还是解压后的？如果是前者，`Segments[].FileOffset`
   会用压缩流的偏移去索引解压后的 buffer，写出去的目标地址就是垃圾。

## 下一步（具体动作）

1. 在 `DarwinBoot.c` 解压分支之后、`AllocateWindow` 之前，用 `DEBUG` 打印：
   `Image`(解压后指针)、`ImageSize`、`Kernel.Base`、`Kernel.Count`、每个段的 `Address/FileOffset/FileSize`。
2. 在 `CopyMem` 循环里打印 `Address + Segments[i].Address - Kernel.Base`。
3. 刷一版，看 `0x1000BF0` 是哪个段算出来的。
4. 如果确认是 `AllocateWindow` 的地址问题，改用 `AllocateMaxAddress` + 显式 `AllocatePages`
   （`AllocateAddress`）拿一块确定可写且被页表覆盖的内存。
5. 修好之后，P2 的路线不变：`rd=md0` → `mockfs`（`_mockfs_mountroot` 已在内核里）→ initrd
   （`out/make-esp.sh` 的 `INITRD=` 已支持，`launchd.macho` 是个打印 `M15OK` 的静态 arm64 替身）。

## 不要重复踩的坑

- `Meizu15Launcher` 的 `Request.BootArgs` 改了没用——启动参数真正来自 ESP 里 `unixnu.toml` 的 `args`
- payload 被 LZMA 压缩在 `FVMAIN_COMPACT` 里，在 FD 明文搜 `FAT16` 永远搜不到
- `GenFw` 的 ADRP→ADR 改写必须关掉（`Elf64Convert.c:1540` 的 `if (mCoffAlignment < 0x1000)` → `if (0)`），
  否则 lld 的 `-r` 产物过不了「requires 4 KB section alignment」
- edk2 链接器用 GNU ld（`-fuse-ld=bfd`）+ edk2 自带的 `-z common-page-size=0x20`，**不要**加
  `-z max-page-size`（会触发 `common page size > maximum page size`）
- `check_all_exports` 在 HakiOS 内核构建里**必然失败**，看 `mach.development.bcm2837` 的时间戳而不是 make 退出码
- 改内核配置后必须手动跑 `python3 tools/hakios-config.py kernel`，否则 `hakios.drivers.h` 不更新
- 虚拟机时钟会跳，`BUILD/obj/.*timestamp*` 落在未来会让 `make` 永久挂起，每次构建前删掉
